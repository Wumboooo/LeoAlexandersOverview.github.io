Case Studies

Problems I solved on the job — what was wrong, what I did, what changed.

Slow ticket page

Performance · PostgreSQL / PHP

Problem: the ticket-create page full-scanned ~27k external rows on every load.
Fix: cached the branch options with a TTL and identified the missing indexes for serial search.
Result: the page no longer pays the full-scan cost per request.

Closed-app push notifications

Mobile · Flutter / FCM

Problem: technicians could miss new tickets when the app was closed.
Fix: an in-app feed plus Firebase push triggered from ticket events, with device registration.
Result: alerts reach technicians even when the app is not open.

Safer releases, three environments

Release · Flutter flavors / Shorebird

Problem: one build pointed at one API, which made testing risky.
Fix: dev / staging / prod Android flavors and per-flavor over-the-air patches.
Result: testing stays off production data and fixes ship without a full reinstall.

Linking tickets to technicians properly

Data model · PostgreSQL / PHP

Problem: request tables tied a technician to a record by matching a name and a text marker, which was fragile.
Fix: added a real technician-ID column to the four request tables, with an idempotent migration and code that still works before the migration runs.
Result: ownership is a plain ID lookup instead of a text match.

One camera standard for six screens

Mobile · Flutter

Problem: six near-duplicate capture screens, and the preview did not match the saved photo.
Fix: defined one standard — a crash guard plus an uncropped, native-aspect preview so what you see is what is saved.
Result: consistent behaviour and fewer camera crashes in the field.

Shipping DB changes without touching live data

Process · SQL migrations

Problem: schema changes on a live ERP are easy to get wrong and hard to undo.
Fix: every change is a dated, idempotent SQL file handed over for review, never run directly on production, and the code degrades gracefully until it is applied.
Result: safe to re-run, easy to review, no surprises on release day.

Catching breakage before release

Quality · PHPStan / ESLint / tests

Problem: a large PHP and JS codebase with several people committing to it.
Fix: static analysis and linting, a single test runner, a browser check before merging, and test-first changes for anything that could crash or touch auth, payments or the database.
Result: risky changes are verified before they reach staging.

“Problem with the app file” on update

Debugging · Android / deployment

Problem: the in-app updater failed with a generic parse error.
Fix: traced it to two causes — the configured download name not matching the uploaded file (so an error page was saved as the APK), and an APK signed with a different key than the installed app.
Result: a clear checklist for publishing updates that install cleanly.

A fair, resilient exam timer

Mobile · Kotlin / Simulingo

Problem: a timed test must not lose or gain time when the user leaves the app.
Fix: a shared countdown that pauses in the background, resumes on return and moves to the next section when time runs out, with answers saved before each move.
Result: sections end on time without losing answers.

Building with AI

Some people look down on using AI to write code. I see it as a tool like any other: used carelessly it produces junk, used well it lets one developer move through any codebase with confidence. I decide what to build and why, the AI speeds up the how, and I review everything that ships.

Directing, not copy-pasting

Prompting · Context

I give the assistant clear goals, the right context and constraints (stack, conventions, what must not change), so the output fits the codebase instead of fighting it.

Verifying every change

Quality · Review

AI-written code goes through the same gates as mine: static analysis, linting, tests, and a manual read-through before it is committed — especially anything touching auth, payments or the database.

Comfortable in any codebase

Productivity · Delivery

Large PHP monolith, Flutter app or a fresh Node project — with AI for debugging, refactors, tests and reading unfamiliar code, I get productive quickly. It doesn't replace understanding; it speeds up how fast I build it.

Always learning the tools

Growth · Adaptability

I keep up with new AI tools and workflows, test what actually helps, and drop what doesn't — so I can onboard fast and work effectively in modern, AI-assisted teams.
